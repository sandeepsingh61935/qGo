Reference · requirements

qGo FR / NFR (interview MVP)

Phrase FR as user capabilities; NFR as system qualities.

Functional requirements

“Users / clients should be able to…”

  1. Enqueue a job with type + payload (optional priority, idempotency key)
  2. Have workers process jobs asynchronously by type
  3. See service health (queue depths / lag signal)
  4. Observe metrics (enqueue / process / fail / depth / lag)
  5. Have failed jobs after max retries land in a dead-letter queue

Non-functional requirements

“The system should be…”

  • Durable enough for learning/prod-like demos: no silent drop on worker crash (processing list + reaper)
  • At-least-once delivery with client idempotency support
  • Low enqueue latency: API returns quickly after Redis write (async work off path)
  • Horizontally scalable workers: more worker processes increase throughput
  • Observable: health + Prometheus metrics for ops questions

Explicitly out of scope (v1)

  • Auth, multi-tenant isolation, delayed/scheduled jobs, priority lanes
  • Exactly-once end-to-end processing
  • Multi-region Redis, strong durability SLA without Redis HA story
