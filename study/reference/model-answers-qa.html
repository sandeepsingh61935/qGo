1. Requirements

Clarify

Q: What are we building?

A: A lightweight async job queue: producers enqueue work; workers process it off the request path. Think mini SQS/Sidekiq for learning and portfolio depth.

FR

Q: What are the functional requirements?

A (model):

  1. Producer can enqueue a job with type + payload (optional priority and idempotency key).
  2. Consumer/worker can process jobs asynchronously by type (handler per type).
  3. Failed jobs are retried, then moved to a dead-letter queue after max attempts.
  4. Operators can check health (queue / processing / DLQ depths, lag signal).
  5. Operators can scrape metrics (enqueued, processed, failed, depth, lag, duration).

Your version mapped: (1) producer send ≈ enqueue · (2) consumer async process · (3) retry — good core; add health/metrics for ops signal.

NFR

Q: What are the non-functional requirements?

A (model — full sentences, not labels):

  1. Latency shape: Enqueue stays fast; heavy work is async (not on the HTTP request).
  2. Durability (worker fault): A single worker crash must not silently drop a claimed job.
  3. Delivery: At-least-once delivery; clients/handlers use idempotency to handle duplicates.
  4. Scalability: Throughput scales by adding worker processes against shared Redis.
  5. Availability: API is useful when Redis is reachable; health reflects that dependency.
  6. Observability: Depth + lag answer “are workers keeping up?” not only success counters.

Your labels: availability, scalability, reliability, durability, throughput/latency — correct themes. Interview answer must expand each into a sentence like above. “Reliability” → prefer durability + delivery + retries/DLQ.

FR vs NFR

Q: Is “use Redis” a requirement?

A: No. That is a design choice. Requirements are needs (enqueue, crash safety). Redis is how we meet latency/simplicity NFRs; we justify it in high-level design.

FR vs NFR

Q: Is retry FR or NFR?

A: Capability “jobs can be retried / DLQ’d” is FR. How aggressive (backoff, max 3, jitter) is design serving reliability NFRs.

2. Back-of-envelope

Estimation

Q: Why do back-of-envelope at all for a small queue?

A: To show you can size workers and storage, and to force trade-offs (one Redis box vs many workers). Even rough orders of magnitude beat silence.

Estimation

Q: Walk me through numbers for qGo (example assumptions).

A (example — state assumptions first):

  • Assume 100 enqueues/s peak, avg job payload ~1 KB, avg process time 100 ms.
  • Worker concurrency: 1 worker core ≈ 10 jobs/s at 100 ms. Need ~10 concurrent slots → e.g. 3 processes × 4 goroutines, headroom for spikes.
  • Ingress bandwidth: 100 × 1 KB ≈ 100 KB/s (trivial).
  • Queue depth: if process rate < enqueue rate by 20/s for 60s → depth grows ~1200 jobs (~1.2 MB) — memory fine; lag is the real alert.
  • Redis memory: depth × size + processing + keys; even 1M jobs × 1 KB ≈ 1 GB order — plan retention / DLQ drain.

Portfolio scale may be tiny; still narrate the method.

Estimation

Q: How do you relate lag, depth, and throughput?

A: Roughly Little’s Law: depth ≈ arrival rate × time-in-system. If lag (oldest job age) rises while enqueue is steady, workers are the bottleneck — scale workers or speed handlers, not the API.

3. API & data model

Lesson: 0004 · Card: api-data-model.html

API

Q: What APIs do you expose?

A:

  • POST /enqueue → 202 { job_id, status: "queued" }
  • GET /health → depths + lag + status (503 if Redis bad)
  • GET /metrics on API · worker metrics on METRICS_PORT (default 9091)

API

Q: Why 202 Accepted instead of 200?

A: 202 means “accepted for async processing.” 200 would imply the work is already done. Enqueue only persists the job; workers run later.

API

Q: When do you return 409?

A: When the client’s idempotency_key already exists (SETNX fails). Same logical request must not create a second job while the key is live.

Data

Q: What does a job look like?

A: JSON on Redis lists: id (UUIDv7), type, payload, priority, idempotency_key, retry_count, created_at, and visibility_deadline while in-flight.

Data

Q: What do you store in Redis?

A:

  • jobs — ready list
  • jobs:processing — in-flight leases
  • jobs:dlq — exhausted failures
  • idemp:{key} — enqueue dedup
  • done:{key} — completion marker

Data

Q: Why no GET /jobs/:id?

A: MVP keeps a single write path and list-based storage. Status lookup needs a secondary index (e.g. job:{id} hash). Easy extension if product needs polling.

4. High-level design

Lesson: 0005 · Card: hld-qgo.html

HLD

Q: Draw the high-level design.

A: Three boxes: API (stateless enqueue/health/metrics) → Redis (ready, processing, DLQ, idemp/done) ← Workers (claim, handlers, reaper). Client only talks to API for writes.

HLD

Q: What are the two main paths?

A:

  • Write: Client → API → Redis RPUSH → 202
  • Process: Worker claim (main→processing) → handler → ack / retry / DLQ

HLD

Q: Why separate API and workers?

A: Scale accept vs processing independently; isolate worker crashes/deploys from enqueue; keep edge thin and pull-based compute.

HLD

Q: What is the source of truth?

A: Redis. API and workers are disposable. Availability of the queue tracks Redis availability.

HLD

Q: 75-second architecture pitch?

A: “Thin API enqueues to Redis and returns 202. Workers pull, claim into processing, run handlers, ack or retry/DLQ. Reaper covers dead workers via visibility timeout. Scale workers for lag; Redis is system of record; watch depth and lag.”

5. Deep dive — claim / lease / ack

Lesson: 0001 · Card: claim-lease-ack.html

Vocabulary

Q: What do claim, lease, and ack mean?

A:

  • Claim — atomically take work: RPOPLPUSH main → processing
  • Lease — temporary ownership via visibility_deadline; if you don’t finish, system assumes failure
  • Ack — success path: remove from processing + set done:{key}

Claim

Q: Why not just LPOP from the main list?

A: LPOP deletes the only copy. Worker dies → job is gone. RPOPLPUSH (Redis reliable-queue pattern) keeps a copy on the processing list until ack.

Failure

Q: Worker dies mid-job. Do we lose the message?

A: No silent loss. Job already sits in processing. No ack → lease expires → reaper moves it back to main → another worker may run it. That is at-least-once.

Failure

Q: Walk the timeline of a crash (30s visibility).

A: t=0 claim + deadline=t+30 → t=5 kill-9 → job stuck in processing → t≈30 reaper requeues → t≈30+ another worker processes again.

Lease

Q: Visibility timeout shorter than job runtime?

A: Reaper requeues while the first worker may still be running → duplicate concurrent execution. Timeout must exceed p99 handler time (or heartbeat/extend lease).

Delivery

Q: Exactly-once?

A: No. We provide at-least-once delivery + idempotent handlers / keys. Exactly-once end-to-end needs much stronger coordination (out of this MVP’s claim).

Reaper

Q: What is the reaper?

A: Not a dependency/library. A background loop in the worker process (~every 10s) that finds processing jobs past visibility_deadline and requeues them to main.

Pitch

Q: 60s answer — “How do you not lose jobs when a worker dies?”

A: “We claim with RPOPLPUSH into a processing list so a crash can’t silently drop the job. That claim has a visibility lease. If the worker dies mid-handler, a reaper requeues after the deadline. Success is an explicit ack. Delivery is at-least-once; handlers must be idempotent.”

5b. Deep dive — idempotency, retries, DLQ

Lesson: 0006 · Card: idempotency-retries-dlq.html

Idempotency

Q: What are the two kinds of “running twice”?

A: (1) Producer double-submit — same logical enqueue twice → SETNX idemp: / 409. (2) Consumer redelivery — lease/reaper after partial work → handler must be safe to re-run; done: after success.

Idempotency

Q: How does enqueue idempotency work?

A: Client sends idempotency_key. We SETNX idemp:{key} with TTL (24h). Fail → 409, no second job. Missing key → use job id (no cross-request dedup).

Idempotency

Q: Does that give exactly-once email send?

A: No. Crash after side effect, before ack, can still redeliver. Keys help; handler/provider idempotency is still required for safe side effects.

Retries

Q: What’s your retry policy?

A: On handler error: increment retry_count; exponential backoff + jitter, cap 60s; after 3 failures → DLQ. Unknown type → DLQ immediately.

DLQ

Q: Why a dead-letter queue?

A: Poison messages must not retry forever and block attention. DLQ keeps {job, error, failed_at} for inspection; alert on dlq_depth.

Pitch

Q: 30s idempotency + 30s retry/DLQ?

A: See lesson spoken answers — two layers of idempotency; max-3 backoff then DLQ; unknown type no retry.

6. Trade-offs (preview)

Trade-off

Q: Why Redis lists instead of Postgres SKIP LOCKED?

A: Redis: simple, low latency, clear primitives for interview story. Trade-off: durability depends on Redis HA/AOF; no free ACID with your business DB. Postgres: stronger durability/transactions, typically lower throughput and more ops weight.
