3. Two paths (draw both arrows)

Write path (producer)

Client → POST /enqueue → API → SETNX idemp → RPUSH jobs → 202

Goal: return quickly; durability of the accept is Redis write success.

Process path (consumer)

Worker → RPOPLPUSH jobs→processing → handle
      → success: LREM + done:key
      → fail: retry later or RPUSH dlq
      → crash: reaper requeues after lease

4. Why split API and worker?

  • Scale independently: many enqueues, few heavy handlers (or reverse).
  • Failure isolation: worker deploy/crash does not take down accept path (while Redis is up).
  • Clear roles: edge is thin; compute is pull-based.

Trade-off: two binaries/processes, metrics are process-local (API vs worker ports).

5. Where is the single source of truth?

Redis holds job state. API and workers are replaceable cattle.

Implication: Redis availability ≈ queue availability. Say that when discussing NFR “availability.”

6. What to postpone to deep dive

On the HLD board, only name these; do not implement yet unless asked:

  • Visibility lease + reaper (crash safety)
  • Idempotency key details
  • Retry backoff / DLQ payload shape
  • Prometheus metric names

Classic move: “I’ll deep-dive crash safety next if that sounds right.”

7. Spoken HLD pitch (~75s)

“Clients call a thin enqueue API. The API validates and writes the job into Redis — ready list plus an optional idempotency key — and returns 202. Stateless API replicas scale with traffic. Workers pull from Redis: claim into a processing list, run a handler by job type, then ack or retry/DLQ. A reaper handles dead workers via visibility timeout. Redis is the system of record; we scale throughput by adding workers, and we watch queue depth and lag.”
