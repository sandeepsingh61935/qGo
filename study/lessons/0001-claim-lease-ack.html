Claim, lease, ack

One skill: narrate a job’s life so a hiring manager hears production judgment — not “I used Redis lists.”

Curriculum note: Start the track at Lesson 0002 — FR / NFR / scope. This lesson is a deep dive after high-level design.

Win for this lesson: a 60-second spoken answer for “How do you not lose jobs when a worker dies?”

Why this matters for your interview

qGo’s interesting design is not the HTTP API. It is the ownership model for work in flight. Interviewers probe whether you understand who owns the job between dequeue and success — and what happens if that owner vanishes.

Three words (learn these)

WordMeaningIn qGo
Claim Atomically take work so two workers do not both “own” the same ready job. RPOPLPUSH from main list → processing list
Lease Temporary right to process; if you do not finish in time, the system assumes you failed. visibility_deadline + reaper scanning processing
Ack Confirm success (or permanent failure path) so the job leaves in-flight state. Remove from processing; set done:{key} on success
Industry name for the lease: visibility timeout (Amazon SQS). While a message is “invisible,” other consumers should not receive it; if you never delete it, it becomes visible again after the timeout. — AWS SQS visibility timeout

Redis reliable queue (why not just LPOP?)

If you only LPOP from the main list and the worker dies, the job is gone — deleted from Redis with no copy. Redis documents a reliable queue pattern: move the item to a processing list with RPOPLPUSH (or modern LMOVE) so a crash leaves the job recoverable. — Redis RPOPLPUSH docs 

READY (jobs)
   │  claim = RPOPLPUSH
   ▼
IN-FLIGHT (jobs:processing)  ←── lease: visibility_deadline
   │
   ├─ success → ack (LREM) + done:key
   ├─ fail    → retry / DLQ
   └─ crash   → lease expires → reaper requeues to READY

The guarantee you must say out loud

At-least-once delivery, not exactly-once.

SQS standard queues store copies for availability; rare server failures can redeliver. Separately, a lease that expires while a slow worker is still working also causes redelivery. Your handler must tolerate duplicates (idempotency). — AWS at-least-once delivery

Script to memorize (≈60s)

“We claim a job with RPOPLPUSH into a processing list so a crash can’t silently drop it. That claim comes with a visibility lease — if the worker dies mid-handler, a reaper requeues after the deadline. Success is an explicit ack: remove from processing and mark the idempotency key done. So delivery is at-least-once; clients pass idempotency keys and handlers must be safe to run twice.”
