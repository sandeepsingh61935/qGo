Back-of-envelope: size the queue

After FR/NFR, interviews often ask for rough math. You do not need precision — you need a clear method and stated assumptions.

Win: Given “100 jobs/s, 100 ms each,” you can estimate worker slots, depth growth, and when lag matters — in under two minutes.

Where this sits in the interview

FR/NFR  →  [you are here: estimate]  →  API  →  HLD  →  deep dive

Model answers for requirements + this section: Model answers (Q&A).

1. Always start with assumptions

Say them out loud before calculating:

  • Arrival rate λ — enqueues per second (peak)
  • Service time S — average handler duration
  • Payload size — bytes per job
  • Retention — how long jobs sit in Redis / DLQ

Example we will use for qGo practice:

λ = 100 jobs/s · S = 100 ms (0.1 s) · size ≈ 1 KB

2. Worker capacity (throughput)

One concurrent handler slot completes about 1 / S jobs per second.

S = 0.1 s  →  1 slot ≈ 10 jobs/s
Need 100 jobs/s steady  →  ~10 slots minimum
Add headroom (spikes, GC, retries)  →  plan ~15–20 slots
e.g. 4 worker processes × 4–5 concurrency

Interview line: “Throughput is limited by concurrent workers × 1/service_time, not by the enqueue API, as long as Redis keeps up.”

3. Queue depth and lag

If workers keep up, depth stays near 0 and lag is tiny.

If enqueue exceeds process rate by Δ for time T:

extra depth ≈ Δ × T
example: 20 jobs/s deficit for 60 s → ~1,200 jobs
memory ≈ 1,200 × 1 KB ≈ 1.2 MB (trivial)
but oldest-job lag ≈ time spent waiting ≈ depth / process_rate
Little’s Law (rough): average number in system ≈ arrival rate × average time in system. Rising lag with steady traffic means workers (or handlers) are the bottleneck — scale workers or optimize work, not the HTTP server.

4. What you watch in qGo

SignalMeaning
queue_depthHow much ready work is waiting
queue_lag_secondsAge of oldest ready job — “are we keeping up?”
processing_depthIn-flight claims (leased work)
dlq_depthPoison / exhausted retries

Portfolio demos may never hit high QPS; still describe these as if on-call.

5. Redis memory (order of magnitude)

jobs in Redis ≈ depth + processing + DLQ
1e6 jobs × 1 KB ≈ 1 GB (plus overhead for keys/lists)
→ DLQ must be drained; unbounded growth is an NFR risk

6. Spoken 60-second template

“Assume 100 jobs/s and 100 ms processing. Each slot does ~10/s, so we need on the order of 10+ concurrent workers with headroom. If we fall behind by 20/s for a minute, depth is ~1.2k jobs — memory is fine, but lag climbs and we’d scale workers. Enqueue bandwidth is ~100 KB/s. Redis memory is depth-driven; we watch depth and oldest-job lag, not just success counts.”

Practice

1. Service time is 50 ms. About how many jobs/s can one slot finish?
2. Enqueue 50/s, process 30/s, for 2 minutes. Approx new depth?
3. Lag rises for 10 minutes; enqueue rate is flat. First lever?

Drill (paper, 3 minutes)

New assumptions: 500 jobs/s, 200 ms avg handle, 2 KB payload.

  1. Min concurrent slots for steady state?
  2. If you only run 50 slots, how fast does depth grow?
  3. Ingress KB/s?

Answers: (1) 500 × 0.2 = 100 slots · (2) process max 50/0.2… wait: 50 slots × (1/0.2)=250/s → deficit 250/s · (3) 500 × 2 KB = 1 MB/s.
