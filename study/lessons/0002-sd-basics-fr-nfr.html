Lesson 0002 · system design from zero · qGo track

Start here: requirements before boxes

System design interviews reward structure. This lesson is the front door: what the interview is, what FR/NFR mean, and how to write them for qGo.

Win: In an interview, you can spend the first 5–8 minutes locking FR, NFR, and out-of-scope — without drawing Redis once.

0. What is a system design interview?

You are not writing production code. You are having a design conversation: clarify the problem, propose a shape, go deep where it hurts, and discuss trade-offs. Jumping to “I’ll put Redis here” before requirements is a common fail.

Industry default is a 4-step process: (1) understand problem & scope → (2) high-level design & buy-in → (3) deep dive → (4) wrap-up. — ByteByteGo / Alex Xu framework; also summarized in Pragmatic Engineer 
[Clarify] → [FR + NFR + Scope] → [Estimate] → [API]
       → [High-level design] → [Deep dives] → [Trade-offs / wrap]

1. Step one output: three lists

The requirements step has a clear deliverable. — interviewing.io: requirements as step 1

ListQuestion it answersInterview phrasing
Functional (FR) What can users / clients do? “Users should be able to…”
Non-functional (NFR) How good / hard / reliable must it be? “The system should be / handle…”
Out of scope What are we not building today? “For v1 we will not…”

2. Functional requirements (FR)

FRs are features and use cases — product behavior. They are not tech choices (“use Kafka”) and not quality targets (“99.99% uptime”). — Hello Interview: functional requirements

Good FR: “A client can enqueue a background job with a type and JSON payload.”

Bad FR: “We will use Redis lists.” ← that’s a design decision.

Bad FR: “Enqueue is under 10ms.” ← that’s an NFR.

qGo — FR for interview MVP

Pretend the interviewer said: “Design a small job queue for async work.” You negotiate down to:

  1. Clients can enqueue a job (type + payload; optional priority & idempotency key).
  2. Workers can process jobs asynchronously by type (pluggable handlers).
  3. Operators can check health (depths / basic liveness of the API path).
  4. Operators can scrape metrics (enqueue, process, fail, depth, lag).
  5. Jobs that fail past max retries go to a dead-letter queue for inspection.

Pocket card: qGo FR/NFR reference

3. Non-functional requirements (NFR)

NFRs are qualities: latency, availability, durability, scale, consistency, security, cost, observability. Phrase them as properties of the system, not user actions. — Hello Interview: NFRs

Good NFR: “Worker crash must not silently drop a claimed job.”

Good NFR: “Enqueue path stays fast; heavy work runs off the request.”

Good NFR: “Delivery is at-least-once; clients can supply idempotency keys.”

qGo — NFR for interview MVP

  • Durability (worker fault): no silent loss on single worker crash (claim into processing + reaper).
  • Delivery: at-least-once; handlers expected to be idempotent.
  • Latency shape: API returns after durable enqueue; processing is async.
  • Scale shape: more worker processes → more throughput (shared Redis).
  • Observability: health endpoint + Prometheus counters/gauges (depth & lag matter).

4. Scope control (what you refuse)

Senior signal: you cut scope on purpose. For qGo v1, say out loud:

  • No auth / multi-tenant isolation
  • No delayed / cron / priority-lane scheduling
  • No exactly-once end-to-end processing
  • No multi-region Redis HA story in v1

This matches how real interviews work: interviewer often agrees to MVP to leave time for deep dives.

5. What is not FR or NFR?

Thing people sayActually is
“Use Redis”Design choice (justify later under NFR: latency/simplicity)
“Use Go”Implementation choice (fine for portfolio; rarely an FR)
“RPOPLPUSH + reaper”Mechanism (deep dive) that serves an NFR
“POST /enqueue”API design (after FR, before or with HLD)

6. Spoken template (first 5 minutes)

Clarify: “Is this a general-purpose job queue for internal services? Who enqueues — our backend only?”

FR: “For MVP: enqueue job, workers process by type, health + metrics, DLQ after N failures.”

NFR: “Async off request path; no silent drop on worker crash; at-least-once with idempotency; workers scale out.”

Out of scope: “No auth, no delayed jobs, no exactly-once, no multi-region in v1. Sound good?”

Wait for interviewer buy-in before drawing boxes.
