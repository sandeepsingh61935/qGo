Idempotency, retries & DLQ

At-least-once is incomplete without a story for duplicates and poison messages. This lesson is that story.

Win: Separate “client double-click” from “worker redelivery,” and walk retry → DLQ without claiming exactly-once.

HLD → claim/lease/ack → [you are here] → metrics/ops → trade-offs

1. Two kinds of “twice”

ScenarioWhat went wrongqGo control
Producer retry Client sends the same logical enqueue twice (timeout, double-click) idempotency_key + SETNX idemp:{key} → second call 409
Consumer redelivery Lease expired / reaper / crash after side effect started Handler must be safe to run again; done:{key} after success reduces re-runs
Interviewers love when you un-merge these. Saying only “we have idempotency keys” without saying where is weak.

2. Enqueue-time idempotency

POST /enqueue { idempotency_key: "pay-42", ... }
  → SETNX idemp:pay-42 = job_id  (TTL 24h)
  → if already set → 409, no second RPUSH
  → else RPUSH job JSON to main list
  • If client omits key, server uses job id (unique each time → no dedup).
  • Dedup window is TTL-bound (24h) — say that if asked “forever?”

Related industry idea: client-supplied idempotency keys on payment/APIs; queue systems use similar dedup tokens.

3. Completion fence (done:)

After successful handle, qGo sets done:{key}. If a reaper requeues a job that already completed (race / double path), dequeue can skip re-running work marked done.

Honest limit: If the handler sent an email, then crashed before ack, redelivery may send again. Keys reduce some races; they do not make side effects magically exactly-once. Handler design (upsert, unique constraints, provider idempotency) still matters.

4. Retries (transient handler failure)

On handler error (or panic recovered as error):

  1. Ack remove from processing (don’t leave a zombie lease for that attempt).
  2. retry_count++
  3. If retry_count >= 3 → DLQ
  4. Else schedule requeue with exponential backoff + jitter, cap 60s
delay ≈ min(2^retry_count seconds + jitter, 60s)
example: 2s, 4s, 8s… (with jitter), never above 60s

Why jitter? Avoid thundering herd when many jobs fail together (e.g. dependency blip).

5. Dead-letter queue (poison / exhausted)

DLQ is a separate list jobs:dlq of records: { job, error, failed_at }.

  • Purpose: stop infinite retry; preserve evidence for humans/tools.
  • Unknown job type: permanent misconfiguration → DLQ immediately (no retry).
  • Ops: watch dlq_depth; draining/replay is a product choice (v1: inspect / manual requeue).

— AWS SQS dead-letter queues

6. How this ties to delivery guarantee

Claim/lease → we don’t lose messages on crash (at-least-once possible).

Idempotency → we survive duplicates (client + consumer).

Retries + DLQ → we bound pain for bad messages (don’t block the queue forever).

Together: practical production-shaped story without lying about exactly-once.

7. Spoken answers

Idempotency (30s): “Two layers. At enqueue, optional client key with SETNX returns 409 on replay so we don’t double-insert. After success we mark done. Redelivery can still happen if we crash mid-handler; the handler must be safe to run twice — keys help, they don’t replace careful side effects.”

Retry/DLQ (30s): “Handler failures increment retry_count, exponential backoff with jitter, max three attempts then DLQ with error metadata. Unknown types go straight to DLQ. We alert on dlq_depth.”
