API & data model

After requirements and rough numbers, lock the contract: what clients call, what a job is, and what Redis stores. Interviewers often ask this before you draw boxes.

Win: On a whiteboard, write endpoints + status codes + job fields + Redis keys in under 90 seconds.

FR/NFR → estimate → [you are here: API + data] → HLD → deep dive

1. Why API design comes before boxes

The API is the product surface. If enqueue is vague, the rest of the design floats. In SD interviews: define write/read paths, success codes, and error semantics first.

2. qGo HTTP surface

EndpointRoleStatus codes
POST /enqueue Producer writes work 202 accepted · 400 bad JSON/type · 409 idempotency conflict · 500 Redis failure
GET /health Liveness + queue signal 200 healthy · 503 Redis unhealthy
GET /metrics Prometheus (API process) 200 text exposition
Worker :9091/metrics Process-local process/retry/lag metrics Separate process (scale workers ≠ API metrics)

Why 202, not 200?

202 Accepted means “we took the work; processing is async.” 200 would imply the job is already done. That matches the NFR: work off the request path.

Enqueue contract

{
  "type": "email.send",          // required — routes to handler
  "payload": { "to": "a@b.com" },
  "priority": 5,                 // stored; v1 does not lane yet
  "idempotency_key": "optional"  // client-supplied dedup
}

// 202 response
{ "job_id": "…", "status": "queued" }

3. Job as the unit of data

One JSON document is the message body on Redis lists:

FieldWhy it exists
idUUIDv7 — unique, time-sortable for debugging
typeHandler dispatch key
payloadOpaque business data (JSON)
idempotency_keyDedup + complete marker; defaults to id if omitted
retry_countDrives backoff / DLQ threshold
created_atLag = now − oldest created_at
visibility_deadlineLease end while in processing
priorityForward-compatible; not scheduled in v1

4. Redis data model (logical schema)

Not tables — lists + string keys keyed by queue name (default jobs):

LIST  jobs                 ready work          (RPUSH enqueue, RPOPLPUSH claim)
LIST  jobs:processing      in-flight leases
LIST  jobs:dlq             poison / max retries
STRING idemp:{key}         SETNX at enqueue     (24h TTL)
STRING done:{key}          SET on success       (24h TTL)

Interview mapping:

  • Ready queue ≈ SQS queue
  • Processing ≈ in-flight / invisible messages
  • DLQ ≈ dead-letter queue
  • idemp/done ≈ application-level dedup / completion fence

5. What we deliberately do not store (for now)

  • No job-status table for GET /jobs/:id (would need extra index)
  • No user/auth tables
  • Priority field exists but no separate priority lists yet

If asked “how would you add status lookup?” → secondary key job:{id} → status or Redis hash updated on transitions.

6. Spoken 60-second answer

“Producers hit POST /enqueue with type and payload; we return 202 and a job id. Optional idempotency key gives 409 on replay. Jobs are JSON on Redis lists: main for ready, processing for leases, DLQ for exhausted failures. String keys track enqueue dedup and completion. Health and metrics expose depth and lag. Workers use a separate metrics port because counters are process-local.”
